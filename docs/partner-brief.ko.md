# 동업자 브리핑 (한 쪽)

코드를 몰라도 읽고 바로 시작할 수 있게 썼습니다. 모르는 말은 맨 아래 용어 설명을 보세요.

## 1. Halo가 뭔가요
Halo는 **AI가 대신 웹사이트를 돌아다니며 일을 해 주는 브라우저**입니다. 크롬처럼 탭이 있고, 거기에 "이거 찾아줘", "이거 비교해줘"라고 말로 시키면 에이전트가 사이트를 열고 클릭하고 정리해 줍니다. 사람이 막히면(로그인, 결제, CAPTCHA) 멈추고 물어봅니다.

차별점으로 삼는 것: 위험한 행동(결제, 개인정보 입력)은 AI가 알아서 하지 못하게 **코드가 막습니다**. AI의 판단에 맡기지 않습니다.

## 2. Halo가 할 수 있는 것 (기능 목록과 체크표)

코드와 화면 정의를 읽어 정리한 목록입니다. **실제로 다 되는지는 확인하지 못했습니다.** 직접 써 보며 맨 오른쪽 칸에 O(됨) / X(안 됨) / ?(모르겠음)를 적어 주세요. X와 ?가 베타 전에 고칠 목록이 됩니다.

- 탭을 끌어서 그룹에 넣기: 없음.
- Halo 앱 자체의 계정과 로그인(Google로 로그인 등): 없음. 계정 없이 내 컴퓨터에서만 동작.

## 3. 하네스(실행 엔진)가 하는 일

**하네스는 에이전트가 일하는 동안 감싸고 있는 안전·복구 장치의 묶음**입니다. AI(플래너)는 "다음에 이걸 하자"고 **제안**만 하고, 실제로 실행하고 검증하고 기록하는 건 하네스(앱의 코드)입니다. AI의 말은 믿지 않는 구조입니다. 동업자가 코드를 볼 필요는 없고, 사용자가 "왜 멈췄지?", "왜 물어보지?"라고 할 때 설명하기 위한 배경 지식입니다.

흐름: 사용자가 시킴 → 앱이 작업의 종류와 길이를 분류 → AI가 다음 행동을 제안 → 앱이 허용 여부를 판단하고 별도의 로컬 승인 서비스에 확인 → 실행 → 효과를 확인하고 기록.

| 하네스 기능 | 쉽게 말하면 | 사용자에게 보이는 곳 |
|---|---|---|
| **짧은/중간/긴 작업 방식** | 작업 길이에 따라 계획, 기억, 저장, 복구를 얼마나 쓸지 달리함. 누가 무엇을 할 수 있는지는 길이와 상관없이 같음 | 직접 보이지 않음(작업 속도와 안정성으로 느낌) |
| **작업 종류 분류** | 일반 브라우징, 화면 기반 컴퓨터 사용, 여러 에이전트, 연구, 루틴 중 어느 방식으로 돌릴지 앱이 정함 | 에이전트의 "능력" 설정 |
| **원래 목표 보존** | 최초의 목표, 제약, 완료 조건을 오래 걸리는 일 중에도, 앱을 껐다 켜거나 사용자가 끼어들어도 잃지 않음 | 작업 화면의 목표와 진행 상태 |
| **여러 작업에 걸친 큰 목표** | 한 프로젝트의 목표를 여러 작업이 이어서 달성함 | 앱 안쪽(백엔드) 기능이라 화면에서 어떻게 보이는지는 개발자에게 확인. 사이드바의 프로젝트 폴더와는 다른 것 |
| **저장과 복구** | 모든 단계를 기록해서 앱이 꺼져도 이어서 할 수 있음. 복구 횟수에도 한도가 있어서 같은 실패를 무한 반복하지 않음 | 작업을 다시 열면 이어짐 |
| **완료 검증** | AI가 "끝났다"고 해도 완료 조건이 확인되기 전에는 완료로 안 침 | "Review"(확인 필요) 상태 |
| **승인 구조** | AI의 제안은 믿지 않고, 앱의 정책과 **별도의 로컬 승인 서비스**가 따로 판단함. 승인은 그 화면 상태에만 유효하고 60초 뒤 만료 | 승인 창 |
| **효과 확인** | 클릭이나 입력 같은 쓰기 동작은 실제로 화면이 바뀐 걸 확인하기 전에는 "성공"으로 보고하지 않음 | 활동 기록 |
| **작업 범위 잠금** | 작업을 시작할 때 정한 제약(어느 사이트만 등)을 AI도 바꿀 수 없음 | 작업 화면의 잠금 표시 |
| **한시 허가** | "이 작업, 이 사이트, 몇 분, 몇 번만"처럼 권한을 빌려주고 시간·횟수가 끝나면 자동 소멸(기본 10분, 3회) | 화면의 허가 표시와 취소 버튼 |
| **읽기 동작 묶음 처리** | 읽기 전용 동작 여러 개를 한 번에 처리해서 AI에 묻는 횟수와 대기 시간을 줄임 | 속도 |
| **메모리 감시** | 앱이 쓰는 실제 프로세스 메모리 합계(기본 한도 2GB)를 재다가 70%, 80%, 90%에서 단계별로 줄이거나 멈춤 | 메모리 때문에 멈추면 멈춤 사유로 표시됨(정확한 문구는 개발자에게 확인) |
| **동시 실행 관리** | 여러 작업을 동시에 돌려도 메모리 한도 안에서만 시작함 | 설정의 실행 방식 |
| **승인 대기 중 계속 일하기(Task Branches)** | 사람 승인을 기다리는 동안, 별도의 읽기 전용 화면에서 다른 페이지를 미리 읽어 둠. 승인될 때만 결과를 합침(승인 하나당 1개, 작업당 2개까지) | 활동 기록(구현 범위는 개발자에게 확인) |
| **여러 에이전트 협업** | 부모 작업이 자식 에이전트에게 읽기 전용 일을 나눠 줌. 자식은 클릭이나 입력을 못 함 | 팀방, 작업 계획 패널 |
| **요소 이름으로 지정(Halowright)** | AI가 "로그인 버튼"처럼 이름으로 지정하면 앱이 실행 순간에 찾아서 처리. 서비스에 MCP가 있으면 그것을 먼저 쓰고 없을 때만 브라우저로 | 직접 보이지 않음(설계됨, 일부 구현) |
| **MCP 도구 제안** | 외부 도구 연결 제안은 권한 모드와 상관없이 **항상 사람의 승인 큐**를 거침 | 승인 창 |
| **플래너 연결과 실패 처리** | AI 연결이 실패하면 분류하고, 설정에 따라 한 단계 위 모델로 다시 시도 | 설정의 "막히면 위 모델로" |
| **기억** | 지역에 저장하는 메모리, 읽은 페이지 기억(Context Awareness, 기본 꺼짐), 활동 기록 | 설정, 에이전트 화면의 메모리 |
| **루틴 실행기와 스케줄러** | 정한 시간에 같은 일을 반복 실행하고, 승인이 필요하면 정한 방식으로 처리 | 홈의 Routines |
| **사용량 기록** | 토큰과 비용을 모델별, 작업별로 집계 | 에이전트 화면의 사용량 |

### 하네스에 대해 솔직하게 말할 한계
- **결제나 위험한 클릭 판단은 버튼 이름의 키워드로 합니다.** 낯선 문구나 다른 언어는 놓칠 수 있습니다. "보장"이라고 말하지 마세요. 놓쳐도 확신이 없는 버튼은 사람 승인으로 가도록 되어 있습니다.
- **메모리 감시는 일정 간격으로 재는 방식**이라, 측정 사이에 순간적으로 치솟는 건 막지 못합니다.
- **Docker나 컨테이너를 켜도 브라우저 작업이 격리되지는 않습니다.** 컨테이너는 `halo/` 게이트웨이(연구용 안전 경계)를 돌리는 것이고, 브라우저 작업은 내 컴퓨터의 앱에서 돕니다.
- **실제 사이트에서의 작업 완료율은 아직 측정한 적이 없습니다.** 베타에서 처음 숫자가 나옵니다.
- **Slack으로 작업을 보내는 기능은** 서명 검증 등 안전 장치는 만들어 두었지만 Slack과 연결되지 않았습니다.

## 4. 지금 어디까지 왔나 (솔직하게)
- 만든 지 3주차, 취미로 시작했습니다.
- **사용자 0명, 데모를 보여 준 적 없음.** 돈을 낸 사람도 없습니다.
- 다른 AI 브라우저(Aside, Atlas, Dia 등)를 써 본 사람 몇 명이 DM을 보냈지만, DM에 대한 답장을 받은 건 **보낸 2~3명 중 1명**뿐입니다. 그 한 문장: "헤일로는 어사이드와 달리 브라우저의 본질을 해치지 않으면 좋겠어요."
- 1월에 **제한적 공개 베타**를 하겠다고 이미 공개로 약속했습니다.

## 5. 두 사람의 역할
- **개발자(코드 담당)**: 코드, 결제와 개인정보 안전 규칙, 버그 수정.
- **당신(사용자와 피드백 담당)**: 사용자에게 말을 걸고, 쓴 사람의 말을 **원문 그대로** 모으고, 직접 써 보고 막힌 곳을 기록합니다.

둘 사이의 연결: 당신이 모은 원문을 개발자가 **일주일에 한 번 읽고**, 가장 많이 나온 것 하나를 다음 주 작업으로 고릅니다.

## 6. 첫 주 과제 (금요일까지)
DM을 보낸 핸들 3~4명에게 아래를 묻고, 답을 **요약하지 말고 그대로** 저장합니다.
1. 어느 브라우저에서 무슨 작업을 시켰나요?
2. 어떻게 실패했나요?
3. 그래서 잃은 게 있나요? (시간, 돈, 잘못된 주문)
4. (답장해 준 1명에게만) "브라우저의 본질"이 구체적으로 뭐예요? 어떤 게 깨지면 바로 닫으세요?

보내는 말은 광고처럼 보이면 안 됩니다. 예시:
> 안녕하세요, 지난번에 남겨 주신 글 봤어요. 저희가 만들고 있는 브라우저 때문에 여쭤봐요. 쓰시던 브라우저에서 어떤 작업이 어떻게 실패했는지 한 가지만 알려 주실 수 있을까요? 홍보 아니고 만들 때 참고하려고요.

답이 안 오면 그것도 결과입니다. "5명에게 보냈고 1명 답함"처럼 숫자를 그대로 적습니다.

## 7. 저장 방법
`docs/tester-reports/날짜-핸들.md` 한 파일에 한 사람씩 붙입니다. 깃을 못 다루면 구글 문서 하나에 모아서 개발자에게 넘겨도 됩니다. 적을 것: 사람(핸들), 날짜, 원문, 내가 한 질문.

## 8. 지켜야 할 것
- **카드, 주민번호, 비밀번호, 인증번호는 받지도 묻지도 않습니다.** 누가 보내 와도 저장하지 말고 지우라고 안내합니다.
- 테스트는 **시험용 계정**으로만 합니다. 개인 계정, 실제 카드는 쓰지 않습니다.
- 환불, 출시 날짜, "안전하다"는 말을 **약속하지 않습니다.** "확인해서 알려드릴게요"까지만 말합니다.
- 사고가 의심되면(시키지 않은 결제 같은 일) 바로 개발자에게 알리고, 사용자에게는 "결제가 필요한 작업은 잠시 하지 말아 주세요"라고만 말합니다. 자세한 순서는 `docs/incident-playbook.ko.md`.

## 9. 지금 하지 않아도 되는 것
가격, 로고, 랜딩 페이지, SNS 계정, 홍보 글. 사용자의 원문이 3개 이상 모이기 전에는 알릴 내용이 없습니다. 마케팅은 그 뒤에 시작합니다.

## 10. 직접 써 보는 것 (선택)
`docs/tester-guide.ko.md`의 작업 5개와 버그 리포트 양식을 쓰면 됩니다. 같은 작업을 다른 AI 브라우저에도 시켜서 결과를 옆에 적어 두면 비교 자료가 됩니다.

## 용어
- **에이전트**: 사람 대신 웹사이트에서 일을 하는 AI.
- **베타**: 정식 출시 전에 몇 명만 먼저 써 보는 시험 단계.
- **원문**: 상대가 쓴 말 그대로. 요약하거나 고치지 않은 것.
- **CAPTCHA**: "로봇이 아닙니다" 확인 화면. Halo는 풀지 않고 사람에게 넘기거나 다른 출처로 돌아갑니다.
- **PR**: 코드 변경을 합치기 전에 사람이 검토하는 요청. 동업자는 몰라도 됩니다.

## 연락
막히면 혼자 오래 붙잡지 말고 바로 개발자에게 묻습니다. 모르는 게 있다는 건 문제가 아니고, 모르는 채로 사용자에게 약속하는 게 문제입니다.
