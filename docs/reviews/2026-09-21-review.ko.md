## 발견 사항

P1은 정상 사용 불능 또는 실행 결과 오인, P2는 결과 정확성·경계 처리·검증 누락, P3는 문서 유지보수 문제다. 아래 내용과 줄 번호는 최초 검수 코드 기준이며 수정 후 현재 코드의 판정은 공통 상태표를 따른다.

### F01 · P1 · 정상 승인·취소 경로에서 중첩 트랜잭션 오류

위치: `halo/gateway.py:115–125`, `:163–166`, `:225`, `:236` 및 revoke의 `BEGIN IMMEDIATE`.

`_db()`가 yield 전에 `_check_clock_rollback()`을 호출하고, 시간이 전진하면 `UPDATE meta`가 SQLite의 암묵적 트랜잭션을 연다. 호출자가 이어서 `BEGIN IMMEDIATE`를 실행해 `OperationalError: cannot start a transaction within a transaction`이 발생한다. Python 회귀 9건이 이 경로에서 실패하며 정상 WSGI 승인도 503이다.

별도 재현에서도 생성 시 clock=1000, 이후 clock=1001로 바꾸고 revoke하면 같은 오류가 발생했다. 트랜잭션 시작 책임을 한 곳으로 모으고 clock watermark·claim·audit의 원자성을 함께 정의해야 한다. 단순히 commit을 끼워 넣으면 경쟁·롤백 의미를 바꾸므로 전체 경계를 검증해야 한다.

### F02 · P1 · 승인 INSERT의 state와 mono_deadline 위치가 뒤바뀜

위치: `halo/gateway.py:230–231`.

열 목록은 `(token,digest,expires,state,mono_deadline)`인데 VALUES는 `(?,?,?,?,'pending')`이다. 네 번째 바인딩인 monotonic deadline이 state에, 문자열 pending이 mono_deadline에 들어간다. F01을 피하는 고정 clock으로 승인하면 다음 행이 실제 저장된다.

```text
typeof(state)='text', state='160.0'
typeof(mono_deadline)='text', mono_deadline='pending'
```

토큰은 반환되지만 실행에서는 `state != 'pending'`으로 거부된다. F01만 고쳐도 정상 실행이 복구되지 않는 독립 결함이다. SQL 바인딩 순서 수정과 저장된 행의 의미·타입을 확인하는 회귀가 필요하다. 잘못 저장된 기존 grant를 승인 상태로 자동 승격해서는 안 된다.

### F03 · P1 · 문서대로 새 인스턴스를 시작할 수 없음

위치: `halo/gateway_app.py:16–28`, `halo/gateway.py:92–94`.

factory가 `O_CREAT`로 빈 DB 파일을 먼저 만든다. 이후 Gateway는 DB 파일이 있는데 realm sidecar가 없다는 이유로 거부한다. 서비스 소유 0700의 새 임시 디렉터리와 유효한 별도 역할 키를 사용해도 `ValueError: existing gateway state has no realm identity; refusing to open`으로 실패했다.

새 DB 생성, realm identity 생성, 기존 DB 마이그레이션을 구분하는 초기화 계약이 필요하다. factory를 통과하는 최초 실행·재시작 테스트도 추가해야 한다. 기존 DB의 identity 검사만 제거하는 방식은 복제 방지 목적을 훼손한다.

### F04 · P1 · 실행 후 clock 오류가 실행 전 거부로 응답됨 — 격리 재현

위치: `halo/gateway.py:245–254`, `:289–295`.

도구가 효과를 발생시킨 다음 wall clock이 역행하면 완료 기록용 `_db()`가 `Rejected`를 던진다. 이것이 WSGI에서 `403 request rejected`로 매핑된다. 실행 후 실패를 반드시 불확실 결과로 알려야 한다는 기존 API 계약과 다르다.

현재 F01·F02가 정상 실행을 먼저 막으므로, 이 항목은 고정 clock과 **임시 DB의 grant 열만 바로잡은 fixture**로 후속 경로를 분리했다. 제품 코드는 변경하지 않았다. 메모리 효과 `['committed']`, DB state=`claimed`, 감사=`approved, claimed`인데 응답은 403임을 확인했다. 현재 일반 요청이 이 경로까지 도달한다는 주장은 아니다.

dispatch 이후 발생하는 완료·감사·시계 오류를 `ExecutionUncertain`으로 보존하고, 원래 예외를 불확실 감사 기록 실패가 덮지 않도록 해야 한다. 같은 토큰의 재생 허용은 관측하지 않았지만, 클라이언트가 효과 미발생으로 오해해 새 승인을 요청할 위험이 있다.

### F05 · P2 · E004 분포 이동 지표에서 배포 가중치를 무시

위치: `experiments/e004_robust_evaluation/experiment.py:261–262`, `rust/halo-experiments/src/e004.rs:312`.

다른 전략에는 변경된 hard-family 비중을 적용하지만 `robust_constrained`에는 equal weighting을 적용한다. 같은 이름의 attack_tpr가 전략별로 다른 모집단을 뜻하게 된다.

seed=7, n=1000 재현:

| 구현 | known TPR | hard TPR | hard 비중 0%의 보고 TPR | hard 비중 100%의 보고 TPR |
|---|---:|---:|---:|---:|
| Python | 99.725% | 61.600% | 80.6625% | 80.6625% |
| Rust | 99.775% | 59.700% | 79.7375% | 79.7375% |

100% hard일 때 mixture TPR은 hard TPR과 같아야 한다. Python 결과는 실제 해당 집단 비율보다 19.0625 percentage points 높게 보고된다. 학습·선택 단계의 equal weighting은 유지할 수 있으나 보고 단계에서는 `macro_tpr`, `mixture_tpr`, `worst_group_tpr`을 구분해야 한다.

### F06 · P2 · robust 선택기가 최소 TPR 제약을 조용히 완화

위치: `experiments/e004_robust_evaluation/experiment.py:171–187`, `rust/halo-experiments/src/e004.rs:236–255`.

benign=[0], hard=[0.1], thresholds=[0.5], max_fpr=0, min_worst=min_any=0.9를 주면 예외나 infeasible 상태 없이 worst_group_tpr=0인 Metrics가 반환된다. 코드에 의도된 fallback이고 Rust 테스트도 그 완화를 기대하지만, 반환 구조에 완화 사실이 없어 호출자가 요청 제약을 만족한 결과와 구별할 수 없다.

strict 선택은 infeasible을 반환하고, 탐색용 완화를 요청한 경우 `constraints_met`, `relaxed_constraints`, `selection_stage`를 명시하는 것이 적절하다. 현재 연구 함수를 실제 권한 게이트로 사용했다는 증거는 없다.

### F07 · P2 · E003 Python/Rust 반올림 차이가 재검증 시점을 변경

위치: `experiments/e003_verdict_freshness/experiment.py:59–60`, `rust/halo-experiments/src/e003.rs:26`.

freshness_window=5, volatility=0.5, delay_steps=3에서 2.5를 Python은 2로, Rust `.round()`는 3으로 반올림한다. 같은 설정에서 Python은 adaptive_window=2·재검증 1회, Rust는 adaptive_window=3·재검증 0회였다. 이는 문서가 허용하는 난수 스트림 차이와 별개의 결정론적 로직 차이다. 경계값 `.5`에 대한 양언어 계약을 정하고 결정론적 fixture로 비교해야 한다.

### F08 · P2 · Rust E003 회귀 기대값이 현재 식과 불일치

위치: `rust/halo-experiments/src/e003.rs:449–460`.

기존 테스트는 window=2, volatility=0.05, delay=4에서 adaptive_window=1·재검증 2회를 기대한다. 현재 Python/Rust 식은 모두 round(1.9)=2여서 재검증 1회가 맞고 실제 실패는 line 459의 left=1, right=2다. F07의 .5 경계 차이와는 별도 문제다. 의도한 freshness 의미를 확정한 후 테스트·주석·실험 설명을 맞춰야 한다. 테스트를 통과시키기 위해 임의로 런타임 식을 바꾸는 것은 연구 의미 변경이다.

### F09 · P2 · trace의 비정상 타입을 일관되게 거부하지 않음

위치: `halo/safety_cases.py:179–205`, `:315–321`.

`Event(kind='tool', action=42, effect=42)`는 findings=[]이며 `decide(..., effectful=True)`도 ALLOW다. 비문자열은 알려진 문자열 검사 자체를 건너뛴다. `metadata=None`은 MONITORING_GAP를 추가한 뒤에도 `.get()`을 호출해 AttributeError로 종료한다.

이 API는 sanitized trace를 받는다고 명시하므로 권한 gateway 우회로 해석할 수는 없다. 다만 untyped telemetry를 방어하는 기존 로직의 취지가 일관되지 않다. 이벤트 진입 시 schema를 확인하고 malformed input을 명시적 오류 또는 MONITORING_GAP로 통일해야 한다. 모델의 문자열 `approved`를 실제 승인 권한으로 승격하는 통합도 금지해야 한다.

### F10 · P2 · 평범한 해시와 수식이 결합되면 secret으로 오탐

위치: `halo/safety_cases.py:100`, `:240–250`.

승인된 upload의 metadata가 `{'sha256': 'a'*64}`이면 findings가 없다. 여기에 별개 필드 `note='x=1'`을 추가하면 SECRET_EGRESS가 발생하고 DENY로 바뀐다. `(?=.*[+/=])`가 동일 토큰 안이 아니라 이후 전체 텍스트의 `=`까지 보기 때문이다. 해시가 secret으로 분류되지 않도록 한다는 바로 위 주석과 모순된다.

문자열을 후보 토큰 단위로 분리해 검사하고, 정상 해시·수식·URL 등에서의 오탐률을 함께 측정해야 한다. 정규식의 존재만으로 entropy가 측정되는 것도 아니다.

### F11 · P2 · adapter fingerprint가 코드 상수 변경을 감지하지 않음

위치: `halo/gateway.py:140–154`.

fingerprint는 filename/name/firstlineno/co_code만 포함한다. 동일 위치의 함수가 1을 반환하는 버전과 2를 반환하는 버전은 co_consts만 다르고 fingerprint가 같다. `types.FunctionType`과 `code.replace(co_consts=...)`로 함수의 실제 반환값은 달라도 hash가 같음을 재현했다. closure/default/global 및 callable 객체도 별도 고려가 필요하다.

이것은 fingerprint 구성 검증이며 외부 요청자가 신뢰된 adapter 코드를 바꿀 수 있다는 공격 증거는 아니다. revision을 그대로 두고 코드가 배포되는 상황의 안전망이 불완전하다. 배포 산출물·설정·의존성 manifest의 명시적 digest를 필수화하고 의미 변경 시 revision을 올리는 계약이 더 검증하기 쉽다.

### F12 · P2 · Rust와 macOS 핵심 경계가 CI 대상에서 빠짐

위치: `.github/workflows/tests.yml:15–33`.

현재 workflow는 Ubuntu/Python 3.12 pytest 하나뿐이다. Rust 테스트 1건이 실제 실패해도 이 CI는 Rust를 실행하지 않으므로 감지할 수 없다. Seatbelt 회귀는 Linux에서 skip된다. gateway factory 최초 시작 테스트도 현재 테스트 파일에서 찾지 못했다.

Rust locked test job, macOS의 제한된 OS runner 검사, clean-start/restart 경로를 CI에 추가해야 한다. runner 자체 테스트의 성공과 security_gate=false를 별개의 결과로 게시해야 한다. 새 테스트가 전체 suite의 수치만 늘리는 대신 F01–F11의 불변식을 직접 확인하도록 한다.

### F13 · P3 · 최신 판정 문서와 근거 링크가 현재 상태에서 벗어남

위치: `REPORT_UNIFIED.ko.md:12`, `:104`, `docs/EVALUATION.md:15–17` 등.

통합 문서의 현재 판정은 Python 183개 이상 통과지만 실제는 174/9다. 추적된 Markdown의 상대 링크 대상 존재 여부를 검사한 결과, 평가 문서의 이전 보고서 이름 20회와 통합 문서의 `CORRECTIONS.ko.md` 1회가 끊어져 있었다. 앵커·외부 URL을 검사한 수치는 아니다. Rust 문서의 과거 57개 통과·OS runner 13개 통과도 현재 실행 수치와 구분해야 한다.

각 판정에 코드 revision, dirty-tree digest, 실행 시각, 원자료 위치를 붙이고 그 상태가 바뀌면 stale로 표시하는 것이 적절하다. 과거 보고서는 역사적 증거로 보존하되 현재 상태를 자동 갱신하는 단일 색인이 필요하다.

## 유지할 장점과 실제 경계

- 탐지 결과와 실행 권한을 분리한 설계가 분명하다. Python Authority의 정확한 요청 결합, 상태 버전 검증, 동시 재생 거부, 사후 감사 손실 경로는 이번 테스트에서 통과했다.
- Rust ProtectedStore는 principal ACL과 monitor 결정을 모두 요구하며 누락·비유한 evidence를 재검증 상태로 처리한다. 관련 회귀가 통과했다.
- E001-B의 상관 실패, E002의 숨은 공격군, E003의 신선도, E005의 적응형 피드백은 실제 설계의 가정을 설명하기 좋은 실험이다. README가 합성 실험을 실제 모델 containment 보장으로 확대하지 않는 점도 타당하다.
- OS runner는 unsupported/error/escaped를 무조건 blocked로 계산하지 않고 잔여 접근을 실패 exit code로 남긴다. 이번 309건의 errors=0, 임시 fixture 제거=true를 확인했다.
- 9개 clean-launch 잔여 사례는 `metadata_access_parent`, `metadata_chdir`, `metadata_fstatat_root`, `metadata_getcwd`, `metadata_getpid`, `metadata_lstat_root`, `metadata_pathconf`, `metadata_statfs`, `metadata_statvfs`다. 일반 파일 탈취나 임의 코드 격리 탈출을 이 9건에서 입증한 것은 아니다. 테스트된 메타데이터 비노출 목표에 실패한 것이다.

## 개선 아이디어와 순서

### 1. 검증 결과와 주장을 연결하는 증거 레지스트리

각 claim에 코드·설정 hash, threat model, 실행 명령, 환경, 표본 수, 결과 파일 hash, 판정(valid/stale/failed/unsupported)을 연결한다. README와 통합 보고서는 이 레지스트리에서 현재 상태를 읽는다. 첫 수용 조건은 gateway 소스 한 줄 변경 시 예전 통과 판정이 stale로 바뀌고, 깨진 로컬 링크가 CI에서 잡히는 것이다. 보고서가 많은 현재 저장소에서 효과가 큰 작업이다.

### 2. E006: 승인부터 효과 대조까지의 장애 실험

기존 gateway를 대상으로 approve→claim→dispatch→audit 사이마다 crash, timeout, clock rollback, 동시 revoke, 백업 복원, worker restart를 주입한다. 임시 파일 쓰기나 메모리 카운터처럼 독립적으로 효과를 확인할 수 있는 adapter를 사용한다. 측정값은 무승인 효과, 중복 효과, 불확실 응답, 잘못된 거부 응답, 복구 시간, 정상 성공률이다. 첫 수용 조건은 한 토큰의 효과가 최대 1회이고 dispatch 후 어떤 실패도 '실행되지 않은 거부'로 보고되지 않는 것이다.

### 3. 실험 공통의 지표 계약과 infeasible 상태

모든 실험이 `count/denominator`, macro·mixture·worst-group 지표, calibration·evaluation 구분, confidence interval, 제약 충족 여부를 공통 포맷으로 출력하게 한다. 표본이 없으면 null과 이유를 남긴다. F05/F06을 먼저 해결하고, 100% 단일 집단 mixture=해당 집단 TPR 같은 대수적 불변식을 Python/Rust 공통 fixture로 검증한다. 양언어가 같은 오류를 복제해도 통과하는 단순 parity 테스트를 보완한다.

### 4. 안전한 실제 작업 replay 벤치마크

합성 점수 다음 단계로 로컬 문서 읽기, 제한된 파일 수정, 임시 수신함에 메시지 쓰기 등 정상 작업과 방해가 섞인 replay corpus를 만든다. 신뢰된 host intent와 관측 trace를 별도로 고정하고, 승인 문자열을 삽입해도 권한이 생기지 않는지 평가한다. 성공률·오탐·재검증 비용·최악 작업군 실패율을 함께 기록한다. 기존 가상 adapter만으로 시작할 수 있으며 실제 모델·외부 서비스 연결은 별도 단계다.

### 5. `halo doctor`와 단일 검증 진입점

가상환경·Rust toolchain·state directory 권한·realm/DB 호환성·schema·신선한 결과 유무를 설명 가능한 출력으로 보여준다. `halo verify --scope python|rust|sandbox|all` 같은 진입점은 테스트 pass와 보안 gate 결과를 각각 출력하도록 한다. 신입 기여자가 오래된 보고서를 순회하지 않고 최초 실행·실패 원인을 재현할 수 있는 것이 수용 조건이다.

권장 실행 순서는 F01–F04와 factory 회귀 → F05–F08의 지표·양언어 의미 → trace schema·오탐·fingerprint → CI/증거 레지스트리 → E006/replay다. 지금은 탐지기 종류를 더 늘리는 것보다 승인·실행 생명주기와 측정 결과의 신뢰도를 높이는 작업이 우선이다.
