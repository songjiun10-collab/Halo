# Payment Mandate — 설계

날짜: 2026-10-13 · 상태: 코어와 컨트롤러 연결 구현됨, 신뢰 UI·실제 결제 흐름 검증은 미구현

## 목적

사람이 채팅으로 결제를 시키면 **바로 결제**하고, 애매하면 **먼저 묻는다.** 돈이 움직이는 일은 실제 사용자가 직접 낸 요청에서만 가능하고, 페이지·모델·루틴·예약 실행이 시작할 수는 없다.

## 흐름

1. **요청 읽기.** 사용자의 채팅(원문 요청과 사용자 권한의 수정 요청)을 host가 결정론적으로 읽는다(`mandateFromUserRequest`). 모델은 판정에 관여하지 않는다.
   - 명확함 = 결제 의도 + 사이트 하나(주소/도메인) + 금액 한도 하나 → **Mandate** 생성(그 task·그 https 사이트·그 통화·한도 이하·1회·기본 30분, 최대 60분). 사람 승인 단계 없이 결제로 진행한다.
   - 애매함 → 아무것도 하기 전에 task를 `need_user`로 멈추고 질문한다: 사이트 없음/여러 곳, 금액 한도 없음/여럿, 송금·이체(받는 사람 확인이 필요하므로 항상 질문).
   - "결제 직전까지만", "사지 마"처럼 결제를 막는 말은 질문이 아니라 명확한 지시다: Mandate 없음, 이후 결제는 기존대로 사람 게이트.
2. **결제 클릭.** 분류기가 결제 버튼(`Pay now`, `Place order`, `결제하기`, `주문하기`…; 송금·출금·계정 삭제는 제외)을 알아보면 host가 읽은 금액(버튼 라벨의 금액, 없으면 `총 결제금액`/`Total` 줄 하나)으로 판정한다(`decidePayment`).
   - 사이트·통화·한도가 맞으면 **pay**: Mandate를 먼저 소진하고 `payment_authorized`를 저널에 남긴 뒤 독립 approver의 판단만으로 실행한다. approver가 deny/review하면 그대로 따른다.
   - 사이트가 다르거나, 통화가 다르거나, 한도를 넘거나, 금액을 못 읽으면 **ask**: task를 멈추고 이유를 묻는다(거부하지 않고 사용자가 정하게 함).
   - Mandate가 없으면 **refuse**: 기존 동작 그대로(텍스트 모드 클릭은 거부, DOM 클릭은 사람 게이트).
3. **사용자의 답.** 답은 수정 요청으로 들어와 목표 버전이 바뀌면 요청을 다시 읽는다. 답 없이 재개하면 같은 질문을 반복하지 않고 결제도 하지 않는다.

## 안전 규칙

- Mandate는 사용자의 채팅 문장에서만 나온다. 루틴·예약 실행(`trigger`)은 Mandate를 받지 않는다.
- 금액은 페이지 텍스트에서 host가 읽는다. 모호하거나 소수점이 통화 단위보다 길면 읽지 못한 것으로 보고 질문한다(반올림 없음).
- 한 목표 버전에서 결제는 한 번뿐이다. 저널에 `payment_authorized`가 있으면 재시작 후에도 새 Mandate를 만들지 않는다.
- Intent Lock이 항상 먼저다. 권한 모드·Lease는 Mandate 없이 결제 클릭을 열 수 없다.
- 카드 정보는 이 경로를 지나지 않는다. 저널에는 사이트·통화·금액·상한·버튼 이름만 남는다.
- 시간은 단조 시계 기준이고, 재시작 시 Mandate는 복원하지 않는다.

## 구현

- `main/harness/payment-mandate.js`: 생성·검증·요청 읽기·금액 읽기·판정·소진.
- `runtime-src/main/harness/effect-classifier.ts`(+생성된 JS): `isPaymentControl`.
- `main/harness/task-controller.js`: `_ensureMandate`(루프 시작에서 질문/생성), `_decidePayment`(결제 클릭 판정).
- 테스트: `test/payment-mandate.test.js`, `test/task-controller-payment.test.js`.

## 아직 안 한 것

- 사이트 이름만 말한 경우(예: "쿠팡")는 주소를 되묻는다. 이름→도메인 매핑은 없다.
- 질문에 답하는 전용 UI(현재는 일반 수정 요청으로 답함)와 결제 완료 표시.
- Electron 엔진에서의 end-to-end 검증(Chromium 엔진에서는 아래대로 확인함).
- 카드 입력(`fillCredential`)과의 연결 검증.

## 검증 (Chromium 엔진, 2026-10-13)

`integration/payment-chromium-e2e.js`: 로컬 TLS 가짜 상점 + 실제 Chromium(CDP 엔진) + 실제 BrowserAdapter/TaskController, 플래너만 스크립트. 결과: 한도 안의 명확한 주문은 상점이 결제(POST)를 정확히 1번 받고, 한도를 넘는 총액은 질문으로 멈춰 상점이 결제를 받지 않으며, 결제 주문이 없는 요청은 사람 승인 대기로 남는다.

이 검증에서 실제 페이지의 관찰 텍스트가 `text`가 아니라 `text` 역할 요소로 나온다는 것을 확인했고, 금액 읽기를 요소까지 보도록 고쳤다(`Subtotal`은 합계로 치지 않는다). root 컨테이너에서는 Chromium 래퍼 스크립트로 `--no-sandbox --ignore-certificate-errors`를 주었다(호스트 코드는 `--no-sandbox`를 금지한다).


## 기본값: 결제는 꺼짐 (옵트인)

호스트 설정 `paymentsEnabled`가 `true`일 때만 위임장(Mandate)이 만들어진다. 값이 없거나 `false`면 위임장을 만들지 않고, 이미 받은 위임장도 취소하며, 결제 클릭은 기존의 사람 승인 단계로 돌아간다. 이유: Halo는 카드를 저장하지 않지만 사용자가 로그인해 둔 사이트의 저장된 결제 수단으로 결제될 수 있으므로, 사용자가 켜기 전에는 결제가 일어나면 안 된다. 컨트롤러 기본값도 꺼짐이라 설정을 전달하는 경로가 빠져도 실패는 "결제 안 됨" 쪽이다. 설정 화면의 스위치는 아직 없다.
