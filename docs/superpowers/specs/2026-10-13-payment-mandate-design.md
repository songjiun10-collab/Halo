# Payment Mandate — 설계 (1단계: 코어)

날짜: 2026-10-13 · 상태: 코어 모듈 구현됨, 컨트롤러·UI 연결은 미구현

## 목적

에이전트가 결제를 대신 진행하더라도, 돈이 움직이는 일은 **실제 사용자가 그 순간 직접 낸 요청**에서만 가능하게 한다. 지금은 돈이 움직이는 클릭(`송금`, `결제하기`, `place order` 등)을 텍스트 모드에서 무조건 거부한다(`effect-classifier`의 `irreversible`). 이 설계는 그 거부를 풀지 않고, 사용자가 만든 좁은 허가증이 있을 때만 사람 승인 단계로 올려 보낸다.

## 핵심 규칙

1. **Mandate는 사용자만 만든다.** 플래너, 페이지, 루틴, 예약 실행, 다른 에이전트, MCP는 만들 수 없다. 생성은 신뢰된 UI 액션(IPC 송신자 검증)으로만 한다.
2. **좁다.** 하나의 task · 하나의 https origin · 하나의 통화 · 최대 금액 · 1회 사용 · 최대 15분(기본 10분). 사용자가 줄일 수만 있고 늘릴 수 없다. 금액은 최소 통화 단위 정수이며 절대 상한이 있다.
3. **금액은 host가 읽는다.** 페이지 텍스트에서 호스트가 읽은 금액이 정확히 하나로 해석될 때만 통과한다(모호하거나 소수점이 통화 단위보다 길면 거부, 반올림 없음). 읽지 못하면 이 경로로는 결제할 수 없고 사용자가 직접 한다.
4. **Mandate는 승인을 대신하지 않는다.** Mandate가 맞아도 그 클릭은 `human_review`로 올라가 사용자가 승인해야 실행된다. 승인 요청에는 host가 읽은 금액·origin·Mandate 상한이 함께 보인다.
5. **무엇도 이것을 우회할 수 없다.** 권한 모드(`full` 포함), Capability Lease, approver의 ALLOW는 결제 클릭을 열 수 없다. Intent Lock의 거부 규칙이 항상 먼저다.
6. **소진·만료.** 사용 즉시 소진, 시간 만료는 단조 시계 기준(벽시계 조작 무효), task 종료·중단 시 폐기. 재시작 시 복원하지 않는다.
7. **카드 정보는 모델에 가지 않는다.** 이 모듈은 카드 데이터를 다루지 않는다. 입력은 기존 `fillCredential` 경로(저장소→필드, 모델에는 값 비노출)를 쓴다.
8. **기록.** `mandate_granted`, `payment_checked`(허용/거부 사유), `payment_authorized`, `mandate_used`, `mandate_expired`를 task 저널에 남긴다. 금액·origin·사유만 남기고 카드 값은 남기지 않는다.

## 구현 상태

- 구현됨: `main/harness/payment-mandate.js`(생성·검증·페이지 금액 파싱·판정·소진)와 `test/payment-mandate.test.js`.
- 미구현(다음 단계):
  - 컨트롤러 연결: `irreversible`로 거부되던 지점에서 Mandate 판정 → `human_review`로 승격, 저널 이벤트, task 종료 시 폐기.
  - 신뢰 IPC: `taskGrantMandate`/`taskRevokeMandate` 및 송신자 검증, 루틴·예약 실행에서는 거부.
  - UI: 금액·origin 입력과 승인창에 host가 읽은 금액 표시.
  - 실제 브라우저 결제 흐름 검증(테스트용 가짜 상점 + 실제 Electron).

## 하지 않는 것

- 모델이 금액을 판정하는 방식(결정론적 보장이 없음).
- 여러 번 결제하는 Mandate, 정기 결제, 자동 승인.
- 카드·계좌 정보의 저장 또는 모델 전달.
