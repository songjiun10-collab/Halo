# Payment Mandate — 설계

날짜: 2026-10-13 · 상태: 코어와 컨트롤러 연결 구현됨, 신뢰 UI·실제 결제 흐름 검증은 미구현

## 목적

사람이 채팅으로 결제를 시키면 **바로 결제**하고, 애매하면 **먼저 묻는다.** 돈이 움직이는 일은 실제 사용자가 직접 낸 요청에서만 가능하고, 페이지·모델·루틴·예약 실행이 시작할 수는 없다.

## 흐름

1. **요청 읽기.** 사용자의 채팅(원문 요청과 사용자 권한의 수정 요청)을 host가 결정론적으로 읽는다(`mandateFromUserRequest`). 모델은 판정에 관여하지 않는다.
   - 명확함 = 결제 의도 + 사이트 하나(주소/도메인) + 금액 한도 하나 → **Mandate** 생성(그 task·그 https 사이트·그 통화·한도 이하·1회·기본 30분, 최대 60분). 사람 승인 단계 없이 결제로 진행한다.
   - 애매함 → 아무것도 하기 전에 task를 `need_user`로 멈추고 질문한다: 사이트 없음/여러 곳, 금액 한도 없음/여럿, 송금·이체(받는 사람 확인이 필요하므로 항상 질문).
   - "결제 직전까지만", "사지 마"처럼 결제를 막는 말은 질문이 아니라 명확한 지시다: Mandate 없음, 이후 결제는 기존대로 사람 게이트.
2. **결제 클릭.** 분류기가 결제 버튼(`Pay now`, `Place order`, `결제하기`, `주문하기`…; 송금·출금·계정 삭제는 제외)을 알아보면 host가 읽은 금액(버튼 라벨의 금액, 없으면 `총 결제금액`/`Total` 줄 하나)으로 판정한다(`decidePayment`).
   - 사이트·통화·한도가 맞으면 **pay**: Mandate를 먼저 소진하고 `payment_authorized`를 저널에 남긴 뒤 독립 approver의 판단만으로 실행한다. approver가 deny/review하면 그대로 따른다.
   - 사이트가 다르거나, 통화가 다르거나, 한도를 넘거나, 금액을 못 읽으면 **ask**: task를 멈추고 이유를 묻는다(거부하지 않고 사용자가 정하게 함).
   - Mandate가 없으면 **refuse**: 기존 동작 그대로(텍스트 모드 클릭은 거부, DOM 클릭은 사람 게이트).
3. **사용자의 답.** 답은 수정 요청으로 들어와 목표 버전이 바뀌면 요청을 다시 읽는다. 답 없이 재개하면 같은 질문을 반복하지 않고 결제도 하지 않는다.

## 안전 규칙

- Mandate는 사용자의 채팅 문장에서만 나온다. 루틴·예약 실행(`trigger`)은 Mandate를 받지 않는다.
- 금액은 페이지 텍스트에서 host가 읽는다. 모호하거나 소수점이 통화 단위보다 길면 읽지 못한 것으로 보고 질문한다(반올림 없음).
- 한 목표 버전에서 결제는 한 번뿐이다. 저널에 `payment_authorized`가 있으면 재시작 후에도 새 Mandate를 만들지 않는다.
- Intent Lock이 항상 먼저다. 권한 모드·Lease는 Mandate 없이 결제 클릭을 열 수 없다.
- 카드 정보는 이 경로를 지나지 않는다. 저널에는 사이트·통화·금액·상한·버튼 이름만 남는다.
- 시간은 단조 시계 기준이고, 재시작 시 Mandate는 복원하지 않는다.

## 구현

- `main/harness/payment-mandate.js`: 생성·검증·요청 읽기·금액 읽기·판정·소진.
- `runtime-src/main/harness/effect-classifier.ts`(+생성된 JS): `isPaymentControl`.
- `main/harness/task-controller.js`: `_ensureMandate`(루프 시작에서 질문/생성), `_decidePayment`(결제 클릭 판정).
- 테스트: `test/payment-mandate.test.js`, `test/task-controller-payment.test.js`.

## 아직 안 한 것

- 사이트 이름만 말한 경우(예: "쿠팡")는 주소를 되묻는다. 이름→도메인 매핑은 없다.
- 질문에 답하는 전용 UI(현재는 일반 수정 요청으로 답함)와 결제 완료 표시.
- Electron 엔진에서의 end-to-end 검증(Chromium 엔진에서는 아래대로 확인함).
- 카드 입력(`fillCredential`)과의 연결 검증.

## 검증 (Chromium 엔진, 2026-10-13)

`integration/payment-chromium-e2e.js`: 로컬 TLS 가짜 상점 + 실제 Chromium(CDP 엔진) + 실제 BrowserAdapter/TaskController, 플래너만 스크립트. 결과: 한도 안의 명확한 주문은 상점이 결제(POST)를 정확히 1번 받고, 한도를 넘는 총액은 질문으로 멈춰 상점이 결제를 받지 않으며, 결제 주문이 없는 요청은 사람 승인 대기로 남는다.

이 검증에서 실제 페이지의 관찰 텍스트가 `text`가 아니라 `text` 역할 요소로 나온다는 것을 확인했고, 금액 읽기를 요소까지 보도록 고쳤다(`Subtotal`은 합계로 치지 않는다). root 컨테이너에서는 Chromium 래퍼 스크립트로 `--no-sandbox --ignore-certificate-errors`를 주었다(호스트 코드는 `--no-sandbox`를 금지한다).


## 기본값: 결제는 꺼짐 (옵트인)

호스트 설정 `paymentsEnabled`가 `true`일 때만 위임장(Mandate)이 만들어진다. 값이 없거나 `false`면 위임장을 만들지 않고, 이미 받은 위임장도 취소하며, 결제 클릭은 기존의 사람 승인 단계로 돌아간다. 이유: Halo는 카드를 저장하지 않지만 사용자가 로그인해 둔 사이트의 저장된 결제 수단으로 결제될 수 있으므로, 사용자가 켜기 전에는 결제가 일어나면 안 된다. 컨트롤러 기본값도 꺼짐이라 설정을 전달하는 경로가 빠져도 실패는 "결제 안 됨" 쪽이다. 설정 화면의 스위치는 아직 없다.

## 카드 정보 블라인드 처리

플래너(모델)와 작업 기록은 카드 정보를 보지 않는다. (`main/harness/card-blind.js`, `task-controller.js`)

- **화면 정보**: 관찰 결과가 플래너로 가기 전에 Luhn 검사를 통과하는 13~19자리 숫자열을 `[카드번호 ••••1111]`처럼 끝 4자리만 남기고 가린다. 카드번호/CVC/유효기간 입력칸(레이블, `autocomplete=cc-*`)의 입력값은 숨긴다.
- **입력 금지**: 카드 입력칸에 타이핑하거나 카드 번호처럼 보이는 텍스트를 입력하려는 동작은 실행하지 않고 `need_user`로 멈춘다. 카드 정보는 사람이 직접 입력한다. 기록에는 `card_input_blocked`만 남고 입력 내용은 남지 않는다.
- **채팅**: 요청이나 수정 메시지에 카드 번호가 있으면 작업을 시작하기 전에 멈추고, 번호를 쓰지 말고 재발급을 고려하라고 안내한다.

**한계 (알고 쓸 것)**
- 화면 캡처(이미지 입력을 쓰는 플래너 경로)는 픽셀을 가릴 수 없다. 결제 입력 화면에서 이미지 입력을 쓰는 플래너를 쓰면 카드 정보가 보일 수 있다. 해결 방법은 아직 구현하지 않았다.
- 채팅에 쓴 카드 번호는 작업 생성 시점에 이미 원문이 기록된다. 멈추고 경고할 뿐 이미 저장된 원문을 지우지는 않는다.
- 숫자열 검사는 Luhn을 통과하는 번호만 가린다. 공백이나 하이픈 이외의 방식으로 쪼개 쓴 번호는 놓칠 수 있다.

## 개인정보 티어 (명시)

호스트가 정하고 모델은 정하지 않는다. 표의 원본은 코드의 `TIER_POLICY`(`main/harness/pii-tiers.js`)이고 이 표는 그 사본이다.

| 티어 | 이름 | 예 | 플래너에게 | 기록(저널)에 | 에이전트의 입력 |
|------|------|----|-----------|-------------|----------------|
| 3 | 비밀 | 카드번호, CVC, 유효기간, 주민등록번호, 비밀번호, 인증번호(OTP), 계좌번호 | 숨김 (카드는 끝 4자리만) | 숨김 | 절대 하지 않음. 사람이 직접 입력 → `need_user`로 멈춤 |
| 2 | 개인 식별 | 전화번호, 이메일 주소 | 보임 | 보임 | 이 작업의 요청에 사용자가 쓴 값과 똑같은 값만 입력. 그 외는 멈추고 확인 |
| 0 | 일반 | 그 외 모든 텍스트 | 보임 | 보임 | 허용 |

- 티어 3은 입력칸(레이블, 비밀번호 타입, `autocomplete=cc-*`)과 값(Luhn을 통과하는 카드번호, 주민등록번호 형식) 두 가지 모두로 판단한다. 주민등록번호가 우연히 카드 Luhn 검사를 통과할 수 있어서 주민등록번호를 먼저 가린다.
- 티어 2의 목적은 에이전트가 페이지에서 본 이메일/전화번호를 다른 곳에 복사해 넣는 유출을 막는 것이다. 사용자가 요청에 직접 적은 값은 그대로 입력한다. 숫자만 같으면(하이픈 유무) 같은 번호로 본다.
- 멈출 때 사유에 `[비밀 정보]` 또는 `[개인 식별 정보]` 티어 표시가 붙고, 기록에는 티어와 동작 종류만 남고 입력 내용은 남지 않는다 (`card_input_blocked`, `personal_input_blocked`).
- 채팅/요청에 티어 3 값이 있으면 작업을 시작하기 전에 멈춘다.

**한계**
- 티어 2는 기록에 그대로 남는다(보이는 정보이기 때문). 기록 암호화/삭제 정책은 별도 과제다.
- 주소, 이름, 생년월일은 아직 티어에서 다루지 않는다(형식이 다양해 오탐이 많다). 필요하면 사용자 설정으로 추가한다.
- (보완됨) 화면 캡처는 가릴 수 없으므로, 비밀 입력칸이나 티어 3 값이 보이는 화면은 이미지를 플래너에 보내지 않고 텍스트 지도만 보낸다(`hasSecretSurface`). 이미지 입력만 되는 어댑터에서는 이런 화면에서 `computer_use_unavailable`로 멈춘다. 텍스트 화면 지도(`screenMap.text`)도 티어 3을 가린다. 한계: 화면에 비밀 정보가 보이는데 DOM에는 없는 경우(캔버스에 그려진 카드 입력창 등)는 감지하지 못한다.
- 로그인 화면처럼 비밀번호 입력칸이 있는 페이지는 이제 항상 텍스트 전용이다. 이미지로만 읽을 수 있는 복잡한 로그인 화면에서는 에이전트가 덜 유능해질 수 있다. 대신 사람이 직접 로그인한다.
- 비밀번호 입력칸에 대한 타이핑은 예전에는 사람 승인 뒤 실행될 수 있었지만, 이제는 승인 대기열에 올리지 않고 바로 사람에게 넘긴다.

## 결제 버튼 감지의 범위와 측정

결제 위임장이 통과시키는 건 "결제 버튼"으로 판정된 컨트롤뿐이다. 판정은 버튼 이름 규칙(`PAYMENT_NAME`, `runtime-src/main/harness/effect-classifier.ts`)이고, 못 잡은 버튼은 위임장 없이 기존 사람 승인 단계로 가므로 **놓침은 마찰이고 오탐은 위험**이다.

**측정 방법**: `fixtures/payment-button-labels.json`에 실제 결제 흐름에서 쓰이는 문구를 한국어, 영어, 일본어로 모으고 정답(결제 확정 단계인지)을 붙였다. `test/payment-detection-corpus.test.js`가 놓침과 오탐을 각각 0으로 요구한다.

| | 문구 수 | 결과 |
|---|---|---|
| 결제 확정 단계(정답: 결제) | 34 | 규칙 확장 전 **18개만 인식(재현율 53%)**, 확장 후 34개 모두 인식 |
| 그 외(장바구니, 결제 수단 추가, 내역, 주문 취소, 구매 확정 등) | 76 | 확장 전후 모두 오탐 0 |

확장 전에 놓친 16개 중에는 `Place your order`(Amazon의 결제 버튼), `Confirm order`, `Complete order`, `Submit order`, `12,500원 결제`, `ご注文を確定する` 등 흔한 문구가 있었다.

**일부러 결제로 보지 않는 것**: `Proceed to checkout`, `Checkout`(결제로 가는 중간 단계), `구매 확정`(받은 물건을 확정하는 뜻으로 쓰는 한국 쇼핑몰 용어), `Pay later`, 결제 수단 추가·변경, 결제·주문·구매 내역. 모호한 짧은 단어(`Purchase`, `결제`, `결제 진행`)는 문구 전체가 그것일 때만 인식한다.

**한계 (알고 쓸 것)**
- 이 문구 모음은 흔한 문구를 기억으로 모은 것이고 실제 사이트에서 긁어 온 것이 아니다. 이 시험은 규칙이 뒷걸음질치지 않게 막는 용도이지 **실제 사이트 커버리지의 증거가 아니다.**
- 이미지로 된 버튼, 아이콘만 있는 버튼, `Pay with PayPal`처럼 다른 사이트로 넘기는 버튼, 이 세 언어 밖의 문구는 다루지 않는다.
- 실제 결제 화면 10곳 이상에서의 확인(설계 문서의 베타 전 항목)은 아직 하지 않았다.
- **확장 방법**: 실제로 놓치거나 잘못 잡은 문구를 만나면 먼저 문구 모음에 정답과 함께 추가해서 시험이 실패하게 만들고, 그다음에 규칙을 고친다. 결제 규칙 파일은 CODEOWNERS의 리뷰 대상이다.
