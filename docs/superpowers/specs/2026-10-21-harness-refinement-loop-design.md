# 하네스 개선 루프 (Harness² 방식 차용)

상태: 초안. 승인 전에는 구현하지 않는다.

## 왜

2026-10-21 측정 결과, 튜닝에 쓴 과제와 새 과제에서 결과가 크게 갈렸다.
조건은 헤드리스, Haiku 5.5(medium)이다. 판정은 Sonnet 5.5가 했고, 글만 보고 스크린샷은 보지 않았다.

| 세트 | 하네스 | 바닐라 |
|---|---|---|
| 튜닝에 쓴 5과제 × 3회 | 8/15 | 3/15 |
| 튜닝에 안 쓴 15과제 × 1회 | 1/15 | 1/15 |

같은 과제의 실패를 보고 손으로 규칙을 고치는 방식은 과적합된다.
Harness² 논문(arXiv 2610.14224)에도 같은 결과가 있다. 시험과 근거 장부 없이 바로 고치게 하면 오히려 떨어졌다.

- WorkBuddy Code: 73.4 → 63.2
- WorkBuddy Web: 69.9 → 65.0

반대로 시험과 장부를 갖춘 1단계 개선은 웹 과제에서 +2.2~+10.4점을 올렸다.
장부, 범위 지정, 합성 단계는 하나씩 뺄 때마다 1.6~3.7점이 빠졌다.

## 무엇을 가져오고 무엇을 안 가져오나

가져오는 것은 방식이다.

1. **제안 → 시험 → 합성.** 수정안을 여러 개 내고, 같은 과제 세트에서 나란히 돌린 뒤, 결과 차이를 보고 고른다.
2. **교훈 장부.** 채택한 수정과 근거를 누적해서 다음 개선 때 참고한다.

가져오지 않는 것은 다음과 같다.

- Harness² 코드. 실행기가 OpenCode와 Codex 전용이고, Vertex AI 인증이 필요하고, 샌드박스를 끈 채 돌린다.
- 과제를 푸는 도중에 개선하는 것. 과제당 k배의 시간과 비용이 들고, 차단하는 사이트에 그만큼 더 접속하게 된다.
  우리는 개발 단계에서만 개선한다. 실제 사용 중에는 고정된 하네스를 쓴다.
- 캡차나 차단 우회. 기존 원칙 그대로다.

## 구성

### 1. 과제 세트를 셋으로 나눈다

- **dev:** 수정안을 시험하는 데 쓴다. 실패 기록을 봐도 된다.
- **holdout:** 채택 여부를 판정할 때만 돌린다. 이 세트의 실패 기록은 보지 않는다.
- **차단 목록:** 헤드리스에서 반복해서 차단되는 사이트다(adoptapet, sec.gov, carvana, cars.com, backcountry 등).
  비교 세트에서 빼고, 차단률은 따로 기록한다.

같은 사이트의 과제가 dev와 holdout 양쪽에 들어가지 않게 나눈다.
논문에서도 같은 분야 안에서만 효과가 컸다(분야를 옮기면 +0.5~+2.9로 줄었다).

### 2. 수정안 후보

후보 하나는 하네스 기본값과의 차이 하나다. 예를 들면 다음과 같다.

- recovery-policy 안내 문구 하나
- 컨트롤러 규칙 하나(예: 지정 사이트 우선)
- 대기 방식 하나(예: 네트워크 idle 대기)

후보마다 켜고 끌 수 있는 플래그를 두어, 같은 코드에서 나란히 돌릴 수 있게 한다.

### 3. 시험

- dev 세트에서 기준 하네스와 후보 2~3개를 각각 3회씩 돌린다.
- 같은 사이트에 동시에 접속하지 않도록 순서대로 돌린다.
- 결과는 통과, 캡차 차단, 사이트 차단, 페이지 열기 실패, 일반 실패로 나눠 집계한다.
- 판정 모델은 기존과 같이 Sonnet 5.5, 글만 보는 방식이다. 바꾸면 비교가 끊긴다.

### 4. 합성

- dev에서 기준보다 나은 후보만 합쳐서 하나의 하네스를 만든다.
- 후보끼리 충돌하면 하나씩 따로 남긴다. 논문에서도 합성 단계를 빼면 성능이 빠졌다.

### 5. 채택 판정

- 합성한 하네스와 기준 하네스를 holdout에서 각각 3회씩 돌린다.
- **채택 조건:** holdout 통과율이 기준보다 높아야 하고, 그 차이가 회차 간 흔들림보다 커야 한다.
- 이 조건을 못 넘으면 코드를 되돌린다. "해가 없으니 남겨 둔다"는 허용하지 않는다.

### 6. 교훈 장부

`apps/computer-browser/bench/lessons.jsonl`에 한 줄에 하나씩 기록한다.

```json
{"id":"site-first","change":"commit 5917ae1","dev":{"base":"2/15","cand":"8/15"},
 "holdout":{"base":"1/15","cand":"1/15"},"adopted":false,
 "note":"튜닝에 쓴 5과제에서만 효과가 있었다"}
```

- 다음 제안 단계에서는 이 장부를 보고, 이미 실패한 방향을 되풀이하지 않는다.
- 채택된 교훈만 프롬프트나 규칙에 남는다.

## 비용과 시간 (추정)

- dev 10과제 × (기준 + 후보 3개) × 3회 = 120회. 회당 약 3분이면 6시간 정도다.
- holdout 10과제 × 2 × 3회 = 60회, 약 3시간이다.
- 모델 호출은 로컬 Claude Code 로그인으로 하므로 API 키 비용은 없다. 시간이 병목이다.
- 처음에는 dev 5과제와 후보 2개로 작게 시작한다.

## 첫 번째 루프에 넣을 후보

1. 이동 직후 내용이 그려질 때까지 대기(browser-adapter `_waitForContent`). 이미 구현했고, medicare에서 효과를 확인하는 중이다.
2. 네트워크 idle 대기. browser-harness의 `wait_for_network_idle` 방식으로, 진행 중인 요청 0개가 500ms 동안 이어지면 끝낸다.
   클릭이나 검색 뒤 결과가 늦게 뜨는 경우를 겨냥한다.
3. 지정 사이트 우선(5917ae1). holdout에서 효과가 없었으므로 끈 상태와 다시 비교한다.

## browser-harness(Browser Use)에서 가져올 것

출처: github.com/browser-use/browser-harness의 README, SKILL.md, `src/browser_harness/helpers.py`. 2026-10-21에 읽었다.

### 가져올 것 (후보 목록에 넣고, 위 루프로 채택 여부를 정한다)

| 항목 | browser-harness | 우리 현재 상태 | 후보 |
|---|---|---|---|
| 내용 대기 | `wait_for_element`: 0.3초마다 요소가 있는지 확인한다 | 이동 직후 빈 페이지를 관찰했다(medicare) | 이미 구현함(`_waitForContent`) |
| 네트워크 대기 | `wait_for_network_idle`: 진행 중인 요청 0개가 500ms 동안 이어지면 끝낸다. 다른 세션의 요청은 무시한다 | 없음 | 클릭이나 검색 뒤에 적용 |
| 관찰 원천 | 접근성 트리(`Accessibility.getFullAXTree`)가 기본이다. 없으면 HTML, 그다음 스크린샷을 쓴다 | 자체 DOM 순회 스크립트를 쓴다 | 요소 이름이 비거나 shadow DOM일 때만 AX 트리로 보충 |
| 클릭 뒤 확인 | 클릭할 때마다 `js()`나 `page_info()`로 결과를 확인한다 | `_withEffectCheck`가 있다 | 변화가 없을 때 재시도 규칙을 비교 |
| 상황별 문서 | interaction-skills: iframes, shadow-dom, dropdowns, dialogs, scrolling 등 18종 | recovery-policy의 안내 문구 | 실패 유형별로 안내 문구를 고르는 방식을 비교 |
| 코드로 시키기 | 모델이 helper를 직접 쓰고, 쓴 helper는 작업 공간에 쌓아 재사용한다 | Halowright 설계만 있다 | 별도 트랙(Halowright 묶음 1) |

### 가져오지 않을 것

- **사람의 실제 Chrome에 붙어 그 로그인 상태로 움직이는 방식.** Halo는 에이전트 창과 사람 창을 분리한다(목표: 백엔드 에이전트는 사용자 창을 건드리지 않는다).
- **캡차나 봇 차단을 Browser Use Cloud(스텔스, 캡차 풀이)로 넘기는 방식.** 원칙상 하지 않는다. 지금처럼 멈추고 사람에게 넘긴다.
- **`wait_for_load()`만 쓰는 방식.** readyState가 complete가 되기를 기다리는 것인데, medicare에서 실패한 우리 방식과 같다.

### 그들의 벤치 수치 (자체 측정, 참고용)

BU Bench V2.1 공개 과제 200개 중 100개를 Codex(GPT-6 Luna)로 쟀다.

| 도구 | 점수 | 과제당 비용 | 과제당 시간 |
|---|---|---|---|
| browser-harness | 60.4 | $0.042 | 9.0분 |
| Playwright MCP | 60.0 | $0.066 | 8.3분 |

점수 차이는 통계적으로 유의하지 않다. 차이가 난 것은 토큰과 비용뿐이다.
"코드로 시키기"가 점수를 올린다는 근거는 이 표에 없다. 비용을 줄인다는 근거만 있다.
Browser Use가 직접 Codex 하나로만 잰 수치다.

## 사용자 의견에서 가져올 것 (GeekNews 댓글, 2026-10-21)

점수가 아니라 "믿고 맡길 수 있나"의 문제라서, 개선 루프와 별도로 제품 시험으로 만든다.

| 원하는 것 | 현재 상태 | 시험 |
|---|---|---|
| 로그인·결제에서 멈추고 사람에게 넘긴 뒤, 하던 자리에서 이어서 하기 | 캡차는 멈추고 Resume 안내(de1c6cd). 결제류는 ASK 방향 | 실제 앱에서 로그인 넘기고 이어 하기. 아직 안 해 봤다 |
| 탭이 닫혀도 어디까지 했는지 남기 | 작업 기록 저장, `resumeSavedTask`로 사람이 재시작 | 탭 강제 종료 후 재시작. 보던 페이지까지 복원되는지 확인 |
| 완료라고 할 때 결과 화면을 다시 보여 주기 | 호스트 검증 단계는 있다(`task-controller.js` finalEvidence). 결과 페이지를 다시 열어 보여 주지는 않는다 | 완료 직전 결과 페이지 재확인 + 화면 제시. 개선 루프 후보로도 넣는다(벤치 실패에 `unverified_report`가 많다) |

### 가져오지 않을 것: 여러 기기를 묶은 스크래핑 팜

- 집의 여러 기기로 대량 스크래핑을 돌리면 사실상 가정용 IP를 여러 개 쓰는 것이 된다. 차단을 IP로 피해 가는 방식이라 "차단 우회 금지" 원칙과 충돌한다.
- 벤치 실패 원인은 차단(약 50%)과 판단 실수였고, 기기 수가 아니었다. 기기를 늘리면 같은 사이트 접속이 늘어 차단만 늘 가능성이 크다.
- 나중 후보: "내 다른 기기에 작업을 넘겨 돌리기"(예: 늘 켜 둔 맥 미니에서 긴 작업, 휴대폰에서 진행 확인과 로그인만 처리). 위 세 가지 시험이 통과한 뒤에 검토한다.

## 열린 문제

- 차단률이 50%에 가깝다. dev와 holdout을 채우려면 차단되지 않는 과제를 더 모아야 한다(Online-Mind2Web 원본에서 추가).
- 판정 모델이 글만 본다. "근거 페이지에서 끝내기"처럼 판정 방식에 유리한 수정이 채택될 수 있다.
  holdout 판정에만 스크린샷을 보는 판정 모델을 추가할지 정해야 한다.
