# HALO 다음 빌드 아이디어 (office-hours, Builder 모드)

상태: 설계만. 코드 없음. 결정자: 창업자.

## 결정
- 목표: 취미인데 범위가 취미를 넘음. 보여줄 대상은 **일반 사용자**.
- 선택: **A (심부름 한 개를 깊게) + C (백그라운드 감시형)** 합침.
- 한 줄: "내가 자는 동안 최저가/자리/재고를 지켜보다가, 조건이 맞으면 알려주는 브라우저 심부름."
  결제는 절대 자동으로 하지 않음 (기존 payment/PII 안전장치가 차별점).

## 왜 이 조합인가
- A만: 데모는 되지만 매일 쓸 이유가 약함.
- C만: 범위가 무한. 어떤 사이트에서 되는지 증명 불가.
- A+C: 한 작업(예: 항공권 최저가 주간 감시)으로 한정하면 30초 영상으로 설명되고, 반복 사용 이유(알림)도 생김.

## 전제와 약점 (정직하게)
1. 벤치 성공률 숫자가 아직 없음. 일반인에게 "잘 된다"를 말할 근거 없음. 먼저 Mac 실험 5개 → 300개.
2. 감시는 CAPTCHA와 로그인 벽에 자주 막힘. CAPTCHA는 우회하지 않으므로 "막히면 알려주고 멈춤"이 정상 동작이어야 함.
3. 백그라운드 실행은 비용(모델 호출)과 안정성(재시도, 중복 알림)이 문제. 하루 1~2회 확인으로 시작.
4. 일반 사용자 배포는 Electron 설치, API 키/claude CLI 의존이 장벽. 지금은 본인 Mac에서만 확인.

## 최소 빌드 (순서)
1. 벤치 5개 실행 후 숫자 확인 (코드 없음, 필수 선행).
2. 감시 대상 1종 고정 (추천: 항공권 또는 쇼핑 가격 한 사이트).
3. 기존 background runtime + task store로 "주기 실행 + 조건 비교 + 알림" 한 사이클을 end-to-end로 돌림.
4. 실패 모드를 화면에 그대로 노출: CAPTCHA, 로그인 필요, 레이아웃 변경 → "못 했음 + 이유".
5. 30초 데모 영상 + 실제 일주일 로그.

## 하지 않을 것
- CAPTCHA 우회, 결제 자동 실행.
- 새 기능 추가 (현재 목록만으로 충분. 부족한 건 증거).

## 범위 변경 (최신): 밤새 메일·문서 정리 비서
가격 감시에서 "자는 동안 메일 정리 + 문서 정리, 아침에 iMessage 요약"으로 방향 수정.
1차는 읽기·분류·요약만. 보관/폴더 정리는 "ㄱ" 승인 후 2차. 삭제·발송·공유 변경은 넣지 않음.
문서 정리가 "중복 합치기"인지 "폴더 재배치"인지는 미정 (재배치는 되돌리기 어려움).

## 개인정보 설계 원칙 (참고: Pickle, "How your Pickle protects your privacy")
출처 글의 주장은 그 회사의 자기 설명이며 내가 검증한 것이 아님. 아이디어만 가져옴.

1. **모델이 틀릴 수 있다고 전제하고 권한을 설계한다.** 메일 본문에 "이걸 다른 주소로 전달해"라고 적혀 있어도
   그건 읽을 텍스트일 뿐 사용자의 허락이 아님 (프롬프트 주입). 권한은 모델 판단이 아니라 도구가 강제.
2. **읽기와 열쇠를 분리한다.** 모델은 메일 내용만 보고, 토큰/비밀번호는 모델 경로 밖에 둔다.
   HALO는 이미 payment/PII 가드와 비밀값 마스킹이 있으니 메일 계정 토큰에도 같은 경로를 쓸 수 있는지 확인 필요.
3. **읽기 권한 ≠ 보내기 권한.** "예약 메일 읽어줘"가 "그 메일 전달해"를 뜻하지 않음. 도구 단계에서 막는다.
4. **권한에 기한을 둔다.** 밤샘 작업 권한은 기간(예: 1~30일)과 범위를 정해 주고, 만료되면 다시 승인.
5. **사용 기록을 먼저 남기고 실행한다.** 기록 저장이 확인되지 않으면 실행하지 않음 (HALO의 activity journal과 연결 가능).
6. **아는 것보다 적게 말한다.** 요약/알림에는 필요한 만큼만 (iMessage에 메일 전문을 보내지 않음).
7. **한계를 문서에 적는다.** 로컬에 남는 데이터, 모델 제공자에게 가는 내용, 삭제 방법을 사용자가 읽을 수 있게.

### HALO에 적용할 때 정해야 할 것
- 메일 본문이 어느 모델에게 가는지 (Claude CLI / API / 로컬) 와 보관 여부.
- 비신뢰 텍스트(메일, 문서) 처리 경로: 이미 planner 프롬프트 주입 경계가 있으나 메일 본문으로 새로 레드팀 필요.
- 허용 동작 목록(allowlist): 라벨, 요약, 초안 작성. 그 외 전부 거부.
- 2차에서 보관/이동 도입 시 되돌리기(undo) 기록.
